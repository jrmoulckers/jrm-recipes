# Internationalization (i18n) workflow

Heirloom ships message catalogs with [next-intl](https://next-intl.dev). The UI renders
whichever catalog the request resolves to (cookie → `Accept-Language` → default), with **English
as the source of truth**. This doc covers how to add or change copy and how to keep the
translated catalogs honest.

## Where things live

| Thing                       | Path                                                         |
| --------------------------- | ------------------------------------------------------------ |
| Locale catalogs             | `src/messages/<locale>.json`                                 |
| Supported locales / default | `src/config/i18n.ts` (`SUPPORTED_LOCALES`, `DEFAULT_LOCALE`) |
| Runtime wiring              | `src/i18n/request.ts`                                        |
| Catalog validator           | `scripts/i18n-validate.mjs` (`pnpm i18n:validate`)           |
| Pseudolocale generator      | `scripts/i18n-pseudo.mjs` (`pnpm i18n:pseudo`)               |

Catalogs are nested JSON grouped by feature namespace (`nav`, `cook`, `recipeEditor`, …). Values
are [ICU message strings](https://next-intl.dev/docs/usage/messages), so placeholders like
`{count}` and `{count, plural, …}` are part of the contract.

## Adding or changing copy

1. Add the key(s) to **`src/messages/en.json`** first. English is the source.
2. Translate the same keys into every other catalog (`es`, `de`, `ar`). Do not copy the English
   value as a placeholder: the validator treats a value that is identical to English as
   untranslated and fails. Copying English is how ~750 keys once shipped looking "in sync" while
   non-English readers saw English.
3. Reference the key in components via `useTranslations`/`getTranslations`.
4. Run `pnpm i18n:validate` and `pnpm typecheck` before pushing.

If a value genuinely is the same in the target language (a brand name, or a word like "Timer" in
German), add it to the allow-list in `scripts/i18n-validate.mjs` so the exemption is explicit
and reviewable rather than silent.

Adding a **new locale**: create `src/messages/<locale>.json`, add the id to `SUPPORTED_LOCALES`
(and the endonym/OpenGraph maps) in `src/config/i18n.ts`, and import it in
`src/i18n/request.ts`.

## Validating catalog parity

```bash
pnpm i18n:validate        # human-readable report, exits non-zero on drift
node scripts/i18n-validate.mjs --json   # machine-readable
```

The validator reads `SUPPORTED_LOCALES`/`DEFAULT_LOCALE` from `src/config/i18n.ts`, flattens
each catalog to dot-delimited keys, and compares every locale against the source. It flags, per
locale:

- **missing keys**: present in the source, absent in the target,
- **extra keys**: present in the target, gone from the source (stale copy),
- **placeholder mismatches**: a shared key whose ICU arguments differ (e.g. the source uses
  `{count}` but the translation dropped or renamed it),
- **untranslated values**: a shared key whose value is byte-identical to the English source,
  meaning the key was copied but never translated.

That last check exists because parity is a check on _structure_ and cannot see _content_. A
catalog can have every key in place and still be entirely English. Values with no run of three
lowercase letters (`OK`, `{count}`, `2x`) carry no signal and are skipped, and justified
collisions live in an explicit allow-list.

It exits `1` when any catalog is out of sync, and runs in CI as the `i18n catalogs` job.

## Pseudolocalization for QA

```bash
pnpm i18n:pseudo                 # writes src/messages/en-XA.json
node scripts/i18n-pseudo.mjs --check   # verify the file is up to date
```

The generator produces `en-XA.json` from the English source: every letter is accented, strings
are bracketed (`[…•••]`) and padded ~40% longer, while ICU placeholders and `<tag>` markup are
preserved so the message still parses. Use it to spot copy that never went through i18n (renders
without brackets) and layout that can't absorb longer languages (truncation/overflow).

`en-XA` is **not** in `SUPPORTED_LOCALES`. It ships nowhere and the validator ignores it. It is
also git-ignored (regenerate on demand). To preview it, point `src/i18n/request.ts` at the
generated catalog temporarily during a QA pass.

## CI note

Both gates run in CI (`.github/workflows/ci.yml`):

- The **i18n catalogs** job runs `node scripts/i18n-validate.mjs`. It needs only checkout and
  Node, no `pnpm install`, because the script has no dependencies.
- The **Lint** job runs `pnpm lint`, which carries the copy ratchet described below.

## The copy ratchet

`i18next/no-literal-string` stops new hardcoded UI copy from reaching JSX. It is applied at two
severities, configured in `.eslintrc.cjs`:

- **`error`** for every area listed in the ratchet override. Those areas have finished
  migrating, so a new literal fails the build.
- **`warn`** everywhere else. That is the remaining backlog.

The backlog is capped by `--max-warnings` in the `lint` script. The number is a high-water mark,
not a target: it may only ever go **down**. When you migrate copy and the warning count drops,
lower the number in `package.json` in the same commit. When an area reaches zero, move it into
the ratchet override so it cannot regress.

Tests, fixtures, and DB seed data are exempt. That override is deliberately the **last** entry
in `overrides`, because later overrides win in ESLint.

Separating this lint gate from the behaviour tests follows
[`ENG-TEST-004`](https://github.com/jrmoulckers/engineering/blob/main/principles/assurance/testing.md)
(distinct static signals).
